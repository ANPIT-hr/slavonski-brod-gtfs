# Plan — Development / Production modes

A redesign of the map viewer into a **two-mode app** with a toggle in the
top-left corner:

- **Development** — the field/editing tools (today's overlay, route tracing, GPS,
  stop dragging). Users can reposition a stop or add a new one and **submit it as
  a recommendation** to a backend queue. We (the developers) review the queue and
  apply the good ones to `gtfs/` for real.
- **Production** — a rider-facing journey planner ("Google-Maps-style"): pick
  *from* and *to*, get which line(s) to take and when, plus a browsable
  timetable of every line. Fully static, runs in the browser.

## Locked decisions

| Decision | Choice | Consequence |
|----------|--------|-------------|
| Recommendations storage | **Vercel KV (Redis)** | Submissions `LPUSH`ed to a list; we read them via a token-gated endpoint + a small review page. |
| Who can submit (dev mode) | **Anyone, light spam protection** | `/api/recommend` rate-limits by IP and validates coords are inside the city bbox. No login. |
| Trip planner engine | **In the browser, no server** | Schedules baked into a data file; a lightweight CSA/RAPTOR runs client-side. Feed is tiny (4,100 stop-times) so it's instant. |

## Feed readiness (already in place)

`gtfs/` has everything the planner needs: `stops` (107), `routes` (8), `trips`
(172), `stop_times` (4,100), `calendar` (3 services) + `calendar_dates` (158
exceptions), `shapes`. No new GTFS authoring required — we only need to **bake
the schedule into a client data file**.

## Architecture

```
                        ┌─────────────────────────────────────────┐
                        │           index.html  (one app)          │

   top-left toggle ───► │  │ DEVELOPMENT │        │ PRODUCTION  │  │
                        │  │ edit tools  │        │ trip planner│  │
                        │  │ + submit    │        │ + timetable │  │
                        │  └──────┬──────┘        └──────┬──────┘  │
                        └─────────┼──────────────────────┼─────────┘
                                  │ POST                  │ reads (static)
                                  ▼                       ▼
                   ┌──────────────────────────┐   data.js (map geometry, stops)
                   │ /api/recommend  (Vercel)  │   schedule.js (trips, times,
                   │   validate + rate-limit   │              calendar, transfers)
                   │   LPUSH → Vercel KV       │           ▲
                   └─────────────┬─────────────┘           │ generated by
                                 │                          │
        review.html  ◄───────────┤ GET /api/recommendations │

                                 ▼                    build_map.py

```

**Static** (no server): the whole viewer, both modes' UIs, the trip planner, the
timetable. **Serverless** (Vercel Functions): only `recommend` (write) and
`recommendations` (read, for us). **Stateful**: Vercel KV holds the queue.

> Vercel root dir is `web/`, so functions live in **`web/api/*.js`** and we add a
> **`web/package.json`** with `@vercel/kv`. Framework preset stays "Other";
> Vercel auto-detects the `api/` folder and installs deps.

## Data pipeline changes (`build_map.py`)

Add a second generated file so production data loads only when needed:

- **`data.js`** (today) — stops + line geometry. Keep as-is; loaded always.
- **`schedule.js`** (new) — loaded lazily when Production mode first opens:
  - `trips`: `{ trip_id, route_id, direction_id, service_id, stops: [[stop_id, dep_seconds], …] }`
  - `services`: resolved calendar — for a given date, which `service_id`s run
    (apply `calendar` weekday mask + `calendar_dates` add/remove exceptions).
  - `transfers`: precomputed walkable stop→stop pairs within a threshold
    (e.g. ≤250 m, walk seconds = dist / 1.3 m·s⁻¹), incl. A/B pole pairs.

Estimated `schedule.js` size: ~150–300 KB uncompressed — fine, and gzipped by
Vercel. Times stored as seconds-after-midnight integers (handles `25:30:00`
past-midnight trips correctly).

## Mode toggle (top-left)

A segmented control pinned top-left, above Leaflet's zoom control:

```
┌──────────────────────┐
│  Razvoj │ Produkcija  │   ← Development | Production
└──────────────────────┘
```

- State persists in `localStorage` **and** the URL (`?mode=dev` / `?mode=prod`)
  so a link can open a specific mode. Default = **Production**.
- Switching mode shows/hides the relevant panel group; the map, line toggles,
  and base-layer switch are shared by both.

## Development mode (spec)

Keeps every current tool (PDF overlay align, route tracing, GPS, stop dragging,
local export). **Adds a submit-to-backend path** on top of the existing
localStorage editing:

1. Enter **Uredi stajališta**, drag a stop to the correct spot (or use 📍 GPS),
   *or* duplicate to propose a **new** stop.
2. New button in the stop popup: **"Pošalji prijedlog"** (Submit recommendation)
   → `POST /api/recommend` with:
   ```json
   { "type": "move" | "new",
     "stop_id": "STOP_KORZO_A", "name": "Korzo",
     "old": {"lat":45.1556,"lon":18.0110},
     "new": {"lat":45.1559,"lon":18.0108},
     "line": "L1|0", "accuracy_m": 8, "note": "pole is 15m north",
     "client_ts": 1730000000000 }
   ```
3. On success: toast "Hvala — prijedlog zabilježen". On rate-limit/validation
   error: friendly message; local edit still persists so nothing is lost.

The existing **Izvezi stops.txt / shapes.txt** exports stay — they're our own
power-tools, independent of the queue.

## Production mode (spec)

### A. Trip planner ("Google-Maps simulator")
- Inputs: **from** stop, **to** stop (searchable dropdowns + "tap on map" + "use
  my GPS → nearest stop"), departure time (default = now), day (default = today).
- Engine: **Connection Scan Algorithm** over `schedule.js`, with footpath
  transfers from the `transfers` table. Returns the 3 best itineraries by arrival
  time, each as legs:
  ```
  14:24  L1  Korzo → Trznica
  14:31  walk 2 min
  14:35  L3  Trznica → Bolnica
  arrive 14:48 · 28 min · 1 transfer
  ```
- Tapping a leg highlights that line + segment on the map.

### B. Timetable browser
- Pick a **line + direction + day** → table of departures (trips × stops), or
  "next departures from this stop" when a stop is selected.
- Honors `calendar` + `calendar_dates`, so holidays/exceptions are correct.

### C. Map
- All lines drawn (shared with dev mode); line on/off toggles remain.

## Backend (Vercel KV + 2 functions)

### `web/api/recommend.js` — POST (public, protected)
- Validate: required fields; `new.lat/lon` inside city bbox
  `[[45.10,17.90],[45.25,18.15]]`; `type ∈ {move,new}`; payload size cap.
- Rate-limit: KV `INCR rl:<ip>` with `EXPIRE 3600`; reject over N/hour.
- Store: `LPUSH recommendations <json>` with a generated `id`, `status:"new"`,
  server timestamp, and hashed IP (not raw). Return `{ ok, id }`.

### `web/api/recommendations.js` — GET/PATCH (token-gated)
- Auth: `Authorization: Bearer $REVIEW_TOKEN` (env var).
- GET: returns the list (optionally filter by `status`).
- PATCH `{ id, status }`: mark `applied` / `rejected` so the queue stays clean.

### Env / setup
- Enable **Vercel KV** in the dashboard, link to the project (injects `KV_*`).
- Add `REVIEW_TOKEN` (random secret) in Project → Settings → Environment Vars.
- `web/package.json` deps: `@vercel/kv`.

### `web/review.html` — our queue (token-gated)
Minimal page: prompts for the token, `GET`s the list, renders each
recommendation with a mini-map (old vs new pin) and **Applied / Rejected**
buttons (PATCH). A "copy as stops.txt row" helper to speed up applying.

## Risks & open questions
- **Walking transfers**: 250 m threshold + 1.3 m/s is a guess; tune against the
  real network (A/B poles must always link). Revisit in Phase 3.
- **Spam**: IP rate-limit + bbox is "light" by design. If it gets abused, add a
  hCaptcha/turnstile check to `recommend` (no UI redesign needed).
- **Past-midnight trips**: handled by seconds-after-midnight, but the planner's
  day-rollover (search window crossing 24:00) needs a test case.
- **`schedule.js` size**: if it grows, switch to fetched JSON + caching instead
  of a `<script>` include.

## Explicitly out of scope (for now)
- Real-time/live vehicle positions.
- Multi-language UI (stays Croatian).
- ~~Wiring `shape_id` into `trips.txt` for full GTFS correctness~~ — **done**, composed at build time by `scripts/build_feed.py`.
- User accounts / edit history per user.

# Part 2 — Google Maps shell redesign (Production mode)

Phases 0–3 above shipped: Production mode already does from/to → CSA routing →
ranked itineraries with a white-cased colored map highlight, plus a timetable
browser. The engine, geocoding, map highlight, and calendar logic are **kept
as-is**. This part is a **UI/UX redesign** to make Production look and behave
like Google Maps transit directions, plus four behavior additions. Development
mode is untouched.

## Goal & decisions (locked with the user, 2026-06-04)

| Decision | Choice |
|----------|--------|
| Layout fidelity | **Full Google Maps shell** — top search card + full-height results sidebar (desktop), bottom sheet (mobile), map fills the rest. |
| Behaviors to add | **All four:** Leave now / Arrive by · step-by-step directions · departure boards · live-ish re-ranking itinerary list. |
| Engine | Reuse the existing CSA. One addition: a **reverse scan for "Arrive by"**. No server. |

## Behavior specs

### 1. Leave now / Arrive by (engine + UI)
- Time-mode segmented control: `Sada | Polazak u | Dolazak do`.
  - **Sada**: depart = current time; auto-refresh the list when reopened /
    every ~60s while idle (the "live-ish" feel).
  - **Polazak u**: current behavior (forward CSA from the chosen time).
  - **Dolazak do**: NEW. Add `planPointsArrive(fromPt, toPt, arrSec, ymd)` — a
    reverse Connection Scan: iterate `ALL_CONNS` by **descending arrival time**,
    track the *latest departure* `dep[stop]` from which you can still reach the
    destination by `arrSec`, seed destination-near stops with egress walk, and
    reconstruct forward. Mirror image of `planPoints`; reuses `TRF`,
    `servicesForDate`, `stopsNear`. `planTopArrive` returns the N latest-leaving
    feasible options.
- ✅ A known arrive-by case returns the latest departure that still arrives in
  time; flipping modes re-runs the search.

### 2. Step-by-step directions (render only — data already present)
- Clicking an itinerary card expands it to a Google-style step list:
  - access walk → "Hodaj N min do {stop}"
  - board → colored line badge, "U {HH:MM} sjedni na {linija} prema {headsign}"
  - "Vozi se N stajališta ({first → last})", optionally an expandable list of
    intermediate stop names (from `tripById(l.trip).stops` sliced board→alight).
  - transfer walk, then egress walk → "Hodaj N min do cilja".
- Tapping a step pans/zooms the map to that leg (reuse `rideRoadSeg`).
- ✅ Stop counts and intermediate names match the GTFS for a 1-transfer trip.

### 3. Departure boards (stop view)
- In Production, clicking a stop marker (markers already `bindPopup`, ~410)
  opens a **departures board** in the sidebar instead of just the popup:
  "Sljedeći polasci s {stop}" — next ~10 departures across all lines serving
  that stop on the selected day, each row: `HH:MM · {badge} {line} → {headsign}`,
  computed from `SCH.trips` filtered by stop + `servicesForDate` + time ≥ now.
- A "Vozni red cijele linije" link opens the existing `renderTimetable` grid
  for that line.
- ✅ Board matches the timetable for a hand-checked stop and day.

### 4. Live-ish itinerary list (render + polish)
- Cards show Google-style summary chips: **total duration**, **arrival–departure
  window**, **# transfers**, **walking minutes**, and the line badges in order.
- The first card is auto-selected and highlighted on the map (as today).
- In "Sada" mode, re-rank/refresh as time advances or inputs change (debounced).
- ✅ Changing the time pickers re-runs and re-sorts without a full reload.
